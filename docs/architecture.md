# Foundation architecture

Next.js App Router provides pages and HTTP endpoints. TypeScript is strict. Better Auth owns credentials, verification/reset tokens, and session cookies; its Prisma adapter persists records in PostgreSQL. Prisma uses the PostgreSQL driver adapter with bounded connection pooling. Server components resolve sessions before reading workspace data.

UI → server route/session check → workspace service → Prisma → PostgreSQL. No client-supplied user identity authorizes a read. `/api/workspaces/:workspaceId` first resolves a verified session and then looks up the composite workspace/user membership. Unauthorized and nonexistent workspaces both return 404 to authenticated callers. Role restrictions are explicit service parameters.

Personal workspace creation is idempotent on unique ownerId. Workspace, OWNER membership, and creation audit are created in a single nested write. Signup provisions immediately; authenticated entry retries provisioning if an interruption left the account without a workspace. Auth user creation and workspace creation are separate transactions, so orphan account recovery is intentional. Multiple memberships are modeled; multiple owned businesses and invitations are deferred.

Business onboarding is an authenticated four-step client experience backed by one server validation schema and one serializable PostgreSQL transaction. Workspace locale/numbering defaults, BusinessProfile, the full PaymentInstruction set, onboarding completion, and the audit event commit together. The request cannot choose a workspace; membership is rechecked inside the transaction. The same form powers later business-settings edits.

Logos are currently limited to 512 KB and stored in PostgreSQL after server-side size, MIME, base64, and file-signature checks. They are served only through an authenticated route. This keeps phase 2 deployable without creating a public filesystem. Move logo bytes behind the planned FileAsset/storage abstraction before receipts or other larger uploads are introduced.

Client records belong directly to a workspace and every read and mutation includes the workspace predicate. OWNER/ADMIN can mutate; STAFF can read. Archive is reversible through `archivedAt`, while a monotonically increasing `version` makes concurrent edits and status changes fail with a 409 instead of overwriting newer data. Client mutations and audit events commit in the same transaction. Lists use stable name/ID ordering and fixed 25-record pages.

Product/service catalog records follow the same authorization, transaction, version, stable-ordering, and pagination pattern. Default prices enter as constrained decimal strings and are converted directly to PostgreSQL `Decimal(19,4)` values. Catalog records inherit the workspace currency for display. Invoice creation will snapshot selected catalog defaults rather than treating the catalog as historical invoice data.

The invoice engine uses one calculation service and the rules in [financial-rules.md](financial-rules.md). API values remain decimal strings until conversion to Prisma Decimal. Line bases, discounts, and taxes are rounded half-up to the currency minor unit; invoice totals sum stored rounded lines. Invoice, items, number allocation and audit event commit in one serializable transaction with bounded conflict retries. Unique workspace/number and composite workspace/client and workspace/invoice foreign keys provide database-level concurrency and tenant guards. Drafts snapshot client and line defaults and use optimistic versions; non-draft edits are rejected.

Issuing transitions a draft to SENT and stores the complete business, client, lines, calculation version, totals and payment instructions as an immutable JSON snapshot. A 256-bit random public token is returned once while only its SHA-256 hash and expiry persist. PDF, public page and email attachment all render from the frozen snapshot. Delivery attempts and invoice events are separate records, so provider acceptance, failure and public-link access remain distinct facts. Rotation replaces the hash and invalidates the previous capability; revocation removes public access.

Payments are append-only ledger entries. Manual recording and confirmation approval lock the invoice row inside a serializable transaction, reject amounts above the remaining balance, and commit Payment, invoice amount/status, InvoiceEvent and AuditLog together. Serialization conflicts are retried; the confirmation-to-payment relation is unique and tenant constrained. Client confirmations remain nonfinancial PENDING records until OWNER/ADMIN review. Payment promises are factual dated events and do not alter balances.

Payment intelligence is calculated from invoice balances, confirmed Payment rows, promises and events on each request. Totals remain separated by currency. Overdue is derived only for SENT/PARTIALLY_PAID invoices with a due date before the workspace-local current date. Active promises suppress overdue attention until their date passes; pending confirmations take priority. Revenue uses payment dates rather than invoice totals.

The follow-up engine stores five workspace-scoped rules and an immutable record of every delivery attempt. Sequence evaluation uses the workspace-local date, selects only the latest newly eligible stage, and deduplicates by invoice, rule and scheduled date. It rechecks invoice state, balance, active promises and pending confirmations inside the serializable preparation transaction. Templates receive the current remaining balance, so partial payments never trigger a full-total request. Email contains the reminder text and frozen invoice PDF; provider acceptance and failure remain distinct invoice events. Dispatch is owner-triggered in Phase 9; a durable scheduled worker remains a launch gate.

Expenses use exact Decimal amounts, explicit currencies, date-only incurred dates and tenant-constrained category references. Records support optimistic correction and audit events; categories archive instead of deleting history. Reports calculate cash revenue from Payment.paidAt, costs from Expense.incurredOn, client revenue from the same payment ledger and aging from current SENT/PARTIALLY_PAID balances. Every total remains separated by currency. CSV exports derive from the same report service as the interface and neutralize spreadsheet formula prefixes.

The PWA manifest launches the authenticated workspace in standalone display mode and provides 192px, 512px, maskable and Apple touch icons. A small client component registers the service worker and shows the browser-controlled install prompt when supported. The service worker caches only the offline document and static icon files. It never intercepts API requests or public invoice capability paths, never stores authenticated page responses, and uses network-only navigation with an offline fallback. Financial work therefore requires a current connection.

Auth objects and Prisma are initialized lazily, preventing database connections during build-time module evaluation. Production environment checks run when server services initialize. No placeholder secret or test authentication fallback is used.

Local email uses a file adapter outside the public directory. Production uses a bounded-time Resend request and reports non-success responses. A durable email outbox, retries, delivery webhooks, and monitoring remain launch gates; this first phase does not claim guaranteed delivery. Auth lifecycle tokens and hashing remain framework-owned.

The UI uses semantic CSS variables, accessible labels, visible focus, reduced-motion support and responsive layouts. No unused accounting navigation or fabricated financial dashboard is shown. PWA installation and offline behavior belong to phase 11.
